# Проверка локальной модели поиска

## Финальный результат: схема v2

По проверкам 15 сентября 2026 года выбрана **Qwen3.5-4B Q8_0** с инструкцией C. В финальном прогоне через настоящий `POST /api/search` она прошла **72 из 76 запросов (94,7%)**: 65/69 представимых фильтров и 7/7 неподдерживаемых запросов. Ожидаемые и фактические ответы, время каждого запроса, параметры, сведения о модели и хеш инструкции опубликованы в [машиночитаемом отчёте](search-model-results.json).

| Набор                             | Правильные ответы | Медиана    | p95         |
| --------------------------------- | ----------------- | ---------- | ----------- |
| Основной, 40 запросов             | 39/40             | 909 мс     | 1398 мс     |
| Дополнительный, 12 запросов       | 12/12             | 936 мс     | 1416 мс     |
| Независимый challenge, 24 запроса | 21/24             | 910 мс     | 1443 мс     |
| Все три набора                    | **72/76**         | **911 мс** | **1422 мс** |

Основной и дополнительный наборы использовались при настройке инструкции. Поэтому их 51/52 — результат на примерах разработки. Challenge из 24 новых запросов подготовил отдельный агент, который не читал актуальные инструкции модели. Его формулировки не использовались при настройке A/B/C; инструкция C была зафиксирована до первого запуска challenge и после него не менялась. Все три набора небольшие: результат не гарантирует такую же точность или задержку для произвольных запросов.

## Что и как проверялось

Схема v2 поддерживает AND/OR, диапазоны, «не равно», исключение названия, сортировку и ограничение количества. [Основной набор](../scripts/fixtures/search-evaluation.json) содержит 38 представимых фильтров и 2 неподдерживаемых запроса; [дополнительный](../scripts/fixtures/search-holdout.json) — 11 фильтров и 1 отказ; [challenge](../scripts/fixtures/search-challenge.json) — 20 фильтров и 4 отказа. Формулировки прежних наборов сохранены при переходе с v1: диапазоны, OR и рейтинги теперь должны давать структурированный фильтр.

[Компаратор](../scripts/search-comparison.mjs) требует `source: ai` и совпадения всего валидного фильтра для представимого запроса, включая числа, операторы, сортировку и лимит. Порядок OR-групп и AND-условий не влияет на сравнение; регистр названия игнорируется. Одинаковые дубли AND и точечный диапазон `gte N AND lte N`, равнозначный `eq N`, нормализуются после проверки полного контракта. Другие преобразования, например `gt N` в `gte N+1`, не выполняются. Для неподдерживаемого запроса нужны `source: text` и полная исходная фраза. Допустимый JSON с потерянным или добавленным условием считается ошибкой, даже если на текущих данных компании результат случайно совпал.

Стенд: AMD Ryzen 7 9800X3D, 64 ГБ RAM, NVIDIA GeForce RTX 5080 с 16 ГБ VRAM, драйвер 616.64; Docker Desktop с WSL2, Docker Engine 28.3.2, Compose 2.38.2 и Ollama 0.34.0. Размещение выбранной модели на видеокарте проверено через `ollama ps`: `100% GPU`.

Параметры финальных запросов: native renderer/parser `qwen3.5`, `think: false`, `temperature: 0`, `num_ctx: 4096`, `num_predict: 2048`, `stream: false`, `keep_alive: 10m` и структурированный ответ по JSON Schema. Seed явно не задавался. Запросы выполняются последовательно; тайм-аут провайдера — 30 секунд, оценочного клиента — 60 секунд. В статистику входит полное время HTTP-запроса, включая серверный разбор; скачивание и первоначальный прогрев модели не входят. Выполнен один проход каждого набора, поэтому задержки зависят от прогрева, кэша и фоновой нагрузки.

Финальная инструкция находится в `searchInstructions` файла [server/search-schema.ts](../server/search-schema.ts). Её SHA-256:

```text
f7979ceb8fa2aab7e0671bfc0eb0235d0cc0e27b68e0c4ddff8f929890a4573a
```

## Оставшиеся четыре ошибки выбранной модели

| Запрос                                                          | Фактическое отличие                        | Почему это ошибка                                                                                                                                                                    |
| --------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| «Первые 7 команд по эффективности, начиная с самых эффективных» | Добавлено `performance > 0`                | Рейтинг исключает команды с нулевой или неизвестной эффективностью, хотя запрос их не исключал.                                                                                      |
| «Нужны дивизионы, в которых суммарно ноль сотрудников.»         | Полная фраза ушла в `source: text`         | Уровень 1 и равенство численности нулю выражаются текущей схемой.                                                                                                                    |
| «Покажи отделы с суммарным бюджетом ровно 2 375 000 рублей.»    | Полная фраза ушла в `source: text`         | Уровень 2 и точное равенство агрегированного бюджета поддерживаются.                                                                                                                 |
| «Три команды с самой низкой средней эффективностью.»            | Добавлено `performance < 9007199254740991` | Порог не отсекает обычные числовые значения, но исключает `null`. По правилам клиента неизвестные значения остаются последними и могут попасть в тройку, если известных меньше трёх. |

Два ответа дают лишнее ограничение, ещё два — ненужный текстовый fallback. Валидатор схемы предотвращает некорректную структуру, но не гарантирует правильное понимание фразы. Эти ошибки сохранены в отчёте; результаты после просмотра challenge не использовались для дальнейшей настройки C.

## Настройка инструкции A/B/C

Все варианты сравнивались на GPU, с `think: false` и одинаковыми параметрами через общий `resolveSearch` и настоящий Ollama. В каждой ячейке показаны **основной / 40 + дополнительный / 12 = сумма / 52**. Все 624 результата двенадцати проб повторно проверены тем же компаратором.

| Модель             | A            | B            | C                |
| ------------------ | ------------ | ------------ | ---------------- |
| Qwen3.5-4B Q4_K_M  | 36 + 11 = 47 | 37 + 10 = 47 | 37 + 12 = 49     |
| Qwen3.5-4B Q8_0    | 36 + 11 = 47 | 38 + 10 = 48 | **39 + 12 = 51** |
| Gemma 4 E2B Q4_K_M | 21 + 7 = 28  | 29 + 10 = 39 | 30 + 10 = 40     |
| Gemma 4 E2B Q8_0   | 23 + 7 = 30  | 32 + 10 = 42 | 33 + 9 = 42      |

A уточняла единицы и обе границы бюджета, сохранение уровня при нулевой численности и отсутствие числовых порогов при ранжировании; в ней оставались шесть прежних примеров. B разделила отбор, порядок и количество результатов и заменила примеры пятью отдельными примерами без OR. C добавила к B одно правило сохранения общих `level/name` в альтернативах и один пример OR. Полные запросы оценочных наборов в примеры инструкции не копировались.

Оба набора из этой таблицы использовались при настройке, включая прежний holdout. Challenge здесь отсутствует: он запускался после фиксации C. Это история разработки инструкции, а не двенадцать независимых испытаний на новых запросах.

Это более ранние прогоны через настоящий `/api/search`, до уточнения правил рейтинга и вариантов A/B/C. Использовались native-импорт, Ollama 0.34.0, `think: false`, температура 0, контекст 4096 и лимит 2048 выходных токенов.

| Модель             | Основной набор | Дополнительный | Всего             | Медиана основного | p95 основного |
| ------------------ | -------------- | -------------- | ----------------- | ----------------- | ------------- |
| Qwen3.5-4B Q4_K_M  | 33/40          | 10/12          | **43/52 (82,7%)** | 7091 мс           | 8720 мс       |
| Gemma 4 E2B Q8_0   | 26/40          | 11/12          | 37/52 (71,2%)     | 2668 мс           | 3891 мс       |

У Qwen один первоначально отклонённый ответ содержал бюджет одновременно `>= 850000` и `<= 850000`; после проверки эквивалентности он засчитан как равенство. Остальные CPU-оценки не изменились. Пересчёт выполнен по сохранённым ответам без повторного вызова модели; исходные отчёты сохранены отдельно.

Перед GPU-сравнением инструкция тоже изменилась: ранжирование само по себе не создаёт числовые пороги, перечисление типов при сортировке не задаёт фильтр уровня, имя руководителя не является названием подразделения. Поэтому изменения точности между этими CPU- и GPU-прогонами нельзя приписывать только видеокарте или квантизации.

## Установка выбранной модели

Проверен прямой импорт текстового `Qwen3.5-4B-Q8_0.gguf` из [репозитория Unsloth](https://huggingface.co/unsloth/Qwen3.5-4B-GGUF), revision `e87f176479d0855a907a41277aca2f8ee7a09523`. Исходный файл занимает **4 482 403 488 байт**, около 4,48 ГБ; SHA-256:

```text
10cc391b403021dd11c614679d2fd92f611c3681d29e29651b717316965d61e1
```

Скачивание, проверка размера и digest и native-импорт с renderer/parser `qwen3.5` завершились успешно. Проектор изображений не скачивался. Непустой прогрев обработал 787 входных токенов и сгенерировал один токен, после чего инициализатор подтвердил готовность. Это отдельная проверка установки и исполнения; качество поиска измерено последующими запросами. Revision и SHA выше относятся к зафиксированному проверенному файлу, а не к обещанию неизменности будущих публикаций Hugging Face.

Отдельно проверен запуск `npm run start:ai` с Qwen Q8 по умолчанию на CPU, без изменения модели и GPU-override: использован кэш, `ollama ps` показал `100% CPU`. Три контрольных запроса через HTTP прошли: `ranking-budget` — 21 572 мс, `range-budget-mixed-units` — 17 671 мс, `or-different-levels` — 20 252 мс. Это проверка запуска и трёх сценариев; полного финального набора на CPU не было. Эти три замера не являются парным сравнением скорости CPU и GPU.

После выбора модели остальные кандидаты и неиспользуемые копии GGUF удалены. Проверка кэша нашла только Qwen3.5-4B Q8_0: один manifest, два используемых blob суммарно 4 482 403 679 байт, без недокачанных, потерянных или неиспользуемых blob. Это состояние файлов в Docker volume; уменьшение физического файла диска WSL2 отдельно не измерялось.

## История: схема v1 из пяти полей

Проверки 14–15 сентября 2026 года: модели Unsloth, Ollama 0.34.0, CPU, контекст 4096, `think: false`, температура 0, лимит 384 выходных токена. Модель предварительно загружена в память. Запросы выполнялись последовательно через настоящий `/api/search`.

Первоначальная схема v1 содержала пять полей и не поддерживала диапазоны, OR или сортировку. Её исходный набор состоял из 23 запросов с представимыми фильтрами и 7 неподдерживаемых запросов. Для первых требовались `source: ai` и совпадение всех пяти полей; для остальных — `source: text` с полной исходной фразой. Проверка JSON сама по себе не считается правильным ответом. Следующая таблица относится именно к этой первоначальной схеме; после её расширения результаты проверяются заново.

| Qwen3.5-0.8B | Q4_K_M                        | HF registry | 0/23               | 6/7                 | 6/30  | 680 мс         | 1355 мс |

Это точность всей связки API и модели по полному контракту. Текстовый fallback сам по себе не различает отказ модели, неверный JSON и тайм-аут. Время зависит от компьютера и фоновой нагрузки; во время оценки 4B параллельно скачивался следующий кандидат. Набор небольшой и не является оценкой точности на произвольных запросах.

`HF registry` — первоначальная установка через Ollama pull с шаблоном из Hugging Face. `Native GGUF` — прямой импорт языкового GGUF без проектора изображений: для Qwen renderer/parser `qwen3.5`, для Gemma — `gemma4-small` / `gemma4` и stop `<turn|>`. Импорт заметно повлиял на ответы 2B; поэтому различия между строками нельзя приписывать только размеру модели или квантизации. Текущий подготовительный скрипт использует единый native-путь для поддержанных моделей Unsloth. При импорте Ollama пересобирает контейнер GGUF через `COPY`, сохраняя типы и байты тензоров; изменение полного SHA не означает изменение весов. [Исходник Ollama](https://github.com/ollama/ollama/blob/v0.34.0/server/quantization.go), [llama.cpp COPY](https://github.com/ggml-org/llama.cpp/blob/b10760/src/llama-quant.cpp).

Версии Qwen 0.8B UD-IQ2_XXS, Q4_K_M и Q8_0, а также Qwen 2B отбракованы и удалены. У 0.8B Q4_K_M модель пропускает уровень, добавляет условия по другим метрикам или возвращает `supported: false` для допустимого запроса. Например, запрос только об эффективности выше 91% добавил ограничения по численности и бюджету. Диапазон бюджета потерял верхнюю границу. Q8_0 правильно обработала все семь неподдерживаемых запросов, но сформировала только один правильный фильтр из 23: этого недостаточно для рабочего поиска.

Дополнительные короткие русские инструкции и ручной chat template результата у 0.8B не исправили. При этом Q4_K_M верно выполнила три простейших контрольных задания: извлечение числа на русском и английском и сопоставление отдела с уровнем 2. Эти наблюдения не доказывают качество других моделей или квантизаций.

У 4B пять допустимых запросов ушли в текстовый поиск, включая запрос только о командах и точное равенство численности. Все 18 выданных AI-фильтров совпали с ожидаемыми; все семь неподдерживаемых запросов сохранились целиком. Это лучший результат Qwen в данном прогоне, но полного прохождения набора пока нет.

Для Gemma исходная смешанная инструкция заменена русской, с явными правилами обязательных полей, единиц бюджета и допустимости поиска по одному условию. Основной набор использовался при этой настройке, поэтому результат 26/30 является результатом на наборе разработки. Точные запросы корпуса не добавлялись в примеры инструкции. Квантизация Q4_K_M после настройки ошиблась на отсутствии сотрудников, бюджете в тысячах, диапазоне бюджета и «не равно». Часть ошибок даёт формально допустимый, но неверный AI-фильтр; JSON Schema не предотвращает такие случаи.

Затем отдельный агент, не читавший новые инструкции, составил `scripts/fixtures/search-holdout.json`: 8 допустимых и 4 неподдерживаемых запроса. Gemma Q4_K_M с русской инструкцией v2 прошла **11/12**: все 8 фильтров и 3/4 отказов, медиана 1317 мс, p95 1857 мс. Ошибка — потерянная верхняя граница диапазона эффективности. Этот небольшой дополнительный набор также не доказывает надёжность на любых формулировках.

Q8_0 с той же инструкцией и старой схемой также дала 11/12 на дополнительном наборе: 8/8 фильтров и 3/4 отказов, медиана 2086 мс, p95 3216 мс. По основному набору смена квантизации не улучшила результат. Файл Q8_0 занимает 5 048 352 864 байта, SHA-256 `605d3c2647d7c58c1e4b5375ccb5702acf94c2611b4c8d4877812f8fdd32d053`; его автоматическое скачивание, импорт и запуск также прошли успешно.

Gemma Q4_K_M загружена из [репозитория Unsloth](https://huggingface.co/unsloth/gemma-4-E2B-it-GGUF), revision `0314792d7f1f7e229411f620751375812bb9faf2`: 3 106 738 272 байта, SHA-256 `740185b21d22ceb83a11c3aa62ad5842ef32c70f6096d756bbee85a1e4ec34b8`. ## Как повторить текущую проверку

Запустить выбранную модель на NVIDIA GPU:

```sh
npm run start:ai:gpu
```

После готовности приложения выполнить в другом терминале все три набора:

```sh
npm run test:search-model -- --output search-main.json
npm run test:search-model -- --fixture scripts/fixtures/search-holdout.json --output search-holdout.json
npm run test:search-model -- --fixture scripts/fixtures/search-challenge.json --output search-challenge.json
```

Для режима CPU используется `npm run start:ai`; `npm start` запускает приложение без модели. Скрипт оценки возвращает код 1 при несовпадениях, сохраняет ожидаемые и фактические фильтры, HTTP-статусы и время каждого запроса. Для другого порта используйте `--base-url http://localhost:18080`; для отдельных примеров — повторяемый `--case ID`.
