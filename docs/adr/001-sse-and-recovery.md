# ADR 001. SSE и восстановление после разрыва

Статус: принято.

## Контекст

Сервер периодически меняет собственные метрики подразделений. Клиенту требуется получать небольшие изменения, сохранять состояние интерфейса и восстанавливаться после потери соединения. Пользовательские команды изменения данных в задании отсутствуют.

## Решение

Использовать HTTP для снимка и Server-Sent Events для одностороннего потока. WebSocket потребовал бы отдельного двустороннего протокола без необходимого здесь обратного канала. Периодический опрос всего дерева передавал бы неизменившиеся данные и создавал лишние пересчёты.

Серверный курсор имеет вид `<instanceId>:<sequence>`. `instanceId` меняется при перезапуске, последовательность растёт на единицу для атомарного пакета реальных изменений. Пустой пакет или запись прежних метрик не меняют курсор, даты и не уведомляют подписчиков.

| Запрос или событие             | Контракт                                                                    |
| ------------------------------ | --------------------------------------------------------------------------- |
| `GET /api/org-tree`            | Плоский массив, заголовки `X-Org-Cursor` и `ETag: "<cursor>"`               |
| `If-None-Match`                | При совпадении текущей ревизии ответ `304` без тела                         |
| `GET /api/org-events?cursor=…` | Подключение с ревизии полученного снимка                                    |
| `Last-Event-ID`                | При наличии имеет приоритет над курсором URL                                |
| `patch`                        | `{ previousCursor, cursor, changes }`; SSE `id` равен новому курсору        |
| `ready`                        | `{ cursor }` после воспроизведения истории; SSE `id` равен текущему курсору |
| `resync`                       | `{ reason }`, после которого сервер закрывает поток                         |

Сервер хранит последние 128 пакетов. Если курсор относится к текущей эпохе и находится внутри доступной истории, отправляются все последующие пакеты в исходном порядке, затем `ready`. Регистрация подписки и воспроизведение синхронны: обновление не может попасть в промежуток между ними. Это закрывает также промежуток между HTTP-снимком и открытием SSE.

Причины `resync`: `missing-cursor`, `invalid-cursor`, `instance-changed`, `history-gap`. Новый экземпляр сервера, устаревшая история и курсор из будущего не восстанавливаются догадками: клиент получает полный снимок.

## Клиентский lifecycle

Перед применением пакета клиент проверяет `previousCursor` относительно текущего кэша, продвижение курсора ровно на единицу и валидирует все изменения. Уже принятая или более старая ревизия той же эпохи не изменяет кэш. Разрыв последовательности запускает восстановление снимка. `ready` дополнительно проверяется относительно актуального курсора. Обычные корректные пакеты записываются напрямую в кэш без `invalidateQueries`.

Контроллер поддерживает состояния подключения, активного потока, переподключения и отсутствия сети. Первый `resync` сразу запрашивает снимок; повторные `resync`, ошибки HTTP и разрывы соединения используют экспоненциальную задержку от 1 до 30 секунд с множителем jitter 0,8–1. Короткое подключение не обнуляет backoff: он сбрасывается после 10 секунд устойчивого соединения. При уходе офлайн поток закрывается; возврат сети позволяет подключиться от последнего применённого курсора.

Снимки и SSE используют общий кэш. Завершившийся позже HTTP-запрос согласуется с текущей ревизией и не откатывает более свежий кэш той же эпохи. Ответ из старого процесса не заменяет уже принятые данные нового процесса. Повторное получение снимка и восстановление подключения управляются контроллером, а не предполагаемым порядком React-рендеров. Контроллер закрывает поток, таймеры и обработчики; проверка поколения соединения отсекает поздние события и продолжения.

Остановка контроллера и переход офлайн отменяют HTTP-восстановление, если этот запрос запустил сам контроллер. Уже выполнявшийся общий запрос, например ручное обновление, к которому контроллер присоединился, таким способом не отменяется. Отдельно снятие последнего наблюдателя TanStack Query передаёт отмену через `AbortSignal`.

## Серверные ресурсы

Комментарий heartbeat отправляется каждые 15 секунд. При `response.write() === false` следующие сообщения попадают в FIFO-очередь; событие `drain` продолжает отправку. Если очередь превысила 64 KiB, медленное соединение закрывается и клиент восстанавливается через журнал. Завершение соединения удаляет его подписку; остановка сервера закрывает потоки и останавливает таймеры.

nginx проксирует SSE без буферизации и с длительным таймаутом. Изменения хранятся только в памяти одного API-процесса: горизонтальное масштабирование потребовало бы общего журнала и согласованной эпохи.
