# ADR 003. Поисковая фраза как проверяемый фильтр

Статус: архитектурное решение принято; локальная модель остаётся экспериментальной.

## Контекст

Пользователь может искать название или сформулировать условие, например «отделы с бюджетом больше 5 млн и эффективностью ниже 80%». Поиск должен работать без API-ключа и при недоступности внешнего сервиса. Результат разбора не должен превращаться в исполняемый JavaScript или подменять данные компании.

## Решение

`POST /api/search` принимает `{ "query": "..." }`: строку длиной от 1 до 500 символов. Сервер преобразует её в небольшой JSON-фильтр и возвращает `SearchResult`. Клиент повторно проверяет схему и применяет фильтр к актуальным агрегатам. Внешней модели передаётся поисковая фраза и описание допустимых полей; дерево компании для разбора запроса не требуется.

```ts
type SearchCondition =
  | { field: 'name'; op: 'contains' | 'notContains'; value: string }
  | { field: 'level'; op: 'eq' | 'ne'; value: 1 | 2 | 3 }
  | {
      field: 'headcount' | 'budget' | 'performance';
      op: 'lt' | 'lte' | 'gt' | 'gte' | 'eq' | 'ne';
      value: number;
    };

type SearchFilter = {
  groups: SearchCondition[][];
  sort: {
    field: 'name' | 'level' | 'headcount' | 'budget' | 'performance';
    direction: 'asc' | 'desc';
  } | null;
  limit: number | null;
};

type SearchResult = {
  filter: SearchFilter;
  source: 'ai' | 'local' | 'text';
  explanation: string;
};
```

Все три ключа фильтра обязательны. Условия внутри группы соединяются через AND, группы — через OR. Пустой `groups` означает отсутствие условий; внутренние группы должны быть непустыми. Допускается не более восьми групп по восемь условий. Диапазон выражается двумя сравнениями одной метрики, `ne` — «не равно», `notContains` — исключением подстроки названия. Лишние ключи и неизвестные операторы отвергаются. Значение числового сравнения должно быть конечным числом от 0 до `Number.MAX_SAFE_INTEGER`; `limit` — целым числом от 1 до 1000 либо `null`. `name` — подстрока без учёта регистра с одинаковой обработкой `е` и `ё`, а не регулярное выражение. Уровень соответствует глубине узла. Числовые условия относятся к агрегатам поддерева; `null`-эффективность не соответствует ни одному числовому сравнению, включая `ne`.

Для примера выше результат имеет вид:

```json
{
  "groups": [
    [
      { "field": "level", "op": "eq", "value": 2 },
      { "field": "budget", "op": "gt", "value": 5000000 },
      { "field": "performance", "op": "lt", "value": 80 }
    ]
  ],
  "sort": null,
  "limit": null
}
```

## Режимы и отказоустойчивость

| `source` | Когда используется                                                                              |
| -------- | ----------------------------------------------------------------------------------------------- |
| `local`  | Выбран режим без модели, вся фраза распознана детерминированным русскоязычным парсером          |
| `ai`     | Сервер получил корректный структурированный ответ настроенной модели                            |
| `text`   | Обычный поиск по названию либо резервный режим при нераспознанной фразе, ошибке или таймауте AI |

Локальный парсер поддерживает заданную грамматику уровней, численности, бюджета с `тыс`/`млн`/`млрд`, эффективности, сравнений, диапазонов, сочетаний условий, исключений по названию и сортировки с ограничением количества. Он возвращает структуру только при понимании всей фразы. Это демонстрационный детерминированный разбор; интерфейс сообщает `local` и не выдаёт его за вызов AI.

Провайдер задаётся через `SEARCH_PROVIDER`: `local`, `ollama` или `openai`. Команда `npm start` явно выбирает `local`; наличие внешнего API-ключа не включает модель. Команда `npm run start:ai` выбирает `ollama`. При прямом запуске сервера без указанного провайдера наличие `AI_API_KEY` выбирает `openai`, иначе используется локальный парсер.

Ollama получает запрос по внутреннему HTTP API `/api/chat`: `stream: false`, `think: false`, JSON Schema, контекст 4096 и предел 2048 выходных токенов. По результатам сравнения выбрана `hf.co/unsloth/Qwen3.5-4B-GGUF:Q8_0` из репозитория Unsloth. Исходный файл `Qwen3.5-4B-Q8_0.gguf` занимает 4 482 403 488 байт, около 4,48 ГБ. Используется только текстовая часть; отдельный проектор изображений `mmproj` не скачивается. При импорте задаются native renderer и parser `qwen3.5`. Явные настройки сохраняют одинаковую конфигурацию при первом и повторных запусках. `OLLAMA_MODEL` позволяет заменить модель или квантизацию, `OLLAMA_URL` задаёт адрес сервиса. Вычисления идут локально на CPU или NVIDIA GPU в зависимости от команды; веса и Ollama не входят в клиентскую сборку. Успешный результат имеет `source: ai`, а пояснение указывает на локальную нейронную модель. Сбой Ollama приводит к текстовому поиску без переключения на облачного провайдера.

Для `openai` используется Responses API со строгой JSON Schema, `store: false` и ограничением вывода. Модель задаётся через `AI_MODEL`, значение по умолчанию — `gpt-4.1-mini`. Серверный `AI_API_KEY` не попадает в клиентские переменные, JavaScript-бандл, ответ API или запрос к Ollama. Тайм-аут по умолчанию — 30 секунд для Ollama и 5 секунд для OpenAI; `AI_TIMEOUT_MS` позволяет его изменить. Отмена клиентского запроса передаётся выбранному провайдеру и действует также при чтении ответа.

Схема не выражает сравнение двух метрик или произвольные вычисления. Данных о прошлых периодах, руководителях и зарплатах для такого поиска нет. Модель получает требование отклонять эти запросы целиком, не отбрасывая непонятные части. Внешний ответ дополнительно проверяется сервером: успешный статус, распознанный запрос, точная схема и наличие хотя бы одного условия, сортировки или ограничения количества. При отказе, некорректном ответе или недоступности AI возвращается поиск по всей исходной строке названия с явным пояснением. Отменённый пользователем запрос не маскируется успешным резервным ответом.

Фраза «Выбери три отдела с самым большим бюджетом» означает группу с `level eq 2`, сортировку `budget desc` и `limit: 3`. Клиент сначала применяет условия и ручной фильтр уровня, затем сортировку запроса и лимит. Состав этой тройки пересчитывается на каждом обновлении агрегатов. Последующая ручная сортировка столбца меняет порядок выбранных строк, сохраняя критерий отбора тройки. Одинаковые значения разрешаются стабильным порядком ID; неизвестная эффективность при сортировке помещается в конец в обоих направлениях.

## Рассмотренные альтернативы

| Вариант                                         | Преимущества                                                                  | Ограничения и причина выбора другого решения                                                                                                                                                                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Только поиск по названию                        | Не требует внешнего сервиса, ключа или сетевого запроса при вводе             | Не выражает условия по уровню, бюджету, численности и эффективности. Сохранён как fallback, но не заменяет поиск естественным языком.                                                                                                 |
| Только локальный парсер                         | Детерминированный результат, работа без ключа и зависимости от доступности AI | Поддерживает заранее заданную грамматику; новые формулировки требуют ручного расширения правил. Используется в демо без ключа, а для разбора других формулировок предусмотрен AI.                                                     |
| Возвращать от AI готовый список подразделений   | Клиенту достаточно показать результат, собственный формат фильтра не нужен    | Модели пришлось бы передавать данные компании. После изменения метрик готовый список может устареть; для повторной проверки условий потребуется новый вызов. Выбран фильтр, который клиент повторно применяет к актуальным агрегатам. |
| Вызывать провайдера непосредственно из браузера | Не нужен серверный маршрут разбора запроса                                    | Настроенный общий API-ключ пришлось бы передавать клиенту. Серверный маршрут сохраняет ключ на сервере и объединяет таймаут, проверку ответа и выбор резервного режима.                                                               |

Выбран серверный разбор с небольшим структурированным фильтром и применением на клиенте: он поддерживает условия по агрегатам, сохраняет их при live-обновлениях и позволяет работать без AI через локальный разбор или текстовый поиск. Цена этого решения — ограниченная выразительность схемы и необходимость поддерживать её в парсере, запросе к модели и клиентской проверке. Поддержка новых операторов или сочетаний условий требует согласованного изменения этих частей.

Для запуска модели выбран отдельный сервис Ollama в Docker Compose. Встраивание GGUF и среды исполнения в браузер увеличило бы загрузку клиента и требования к устройству пользователя. Обязательная ручная установка Ollama усложнила бы запуск. Дополнительный Compose-файл устанавливает среду в контейнере, а подготовительный сервис скачивает отсутствующую модель и прогревает её в фоне. API и интерфейс запускаются независимо: скачивание нескольких гигабайт не должно мешать просмотру оргструктуры. Это сохраняет запуск одной командой ценой ожидания готовности умного поиска и дополнительной памяти на сервере. Docker с Compose остаётся системным условием; базовый режим запуска модели не требует.

Подготовительный сервис остаётся работающим после завершения подготовки и отдаёт состояние через внутренний HTTP-маршрут. API проверяет его ответ и публикует только состояние в `GET /api/search/status`; адрес сервиса задаётся через `MODEL_STATUS_URL`. Это позволяет отличать скачивание, прогрев и ошибку без доступа API к Docker socket или общему записываемому файлу. Тайм-аут либо недоступность сервиса отображаются как `unavailable`, а не как бесконечная загрузка. Healthcheck контейнера означает доступность маршрута состояния, готовность модели — отдельное значение `ready`.

Перед запуском Compose общий npm-скрипт проверяет готовность Docker. На Windows/macOS он может запустить установленный локальный Docker Desktop через его CLI и дождаться движка. Это устраняет необходимость вручную открывать Docker Desktop после перезагрузки компьютера. Установка Docker и настройка Linux или удалённого движка остаются системными условиями.

GPU вынесен в отдельный `docker-compose.gpu.yml` и команду `npm run start:ai:gpu`. Контейнер получает доступ к NVIDIA GPU, а подготовка и кэш модели остаются общими с `start:ai`. Это сохраняет возможность запуска на CPU без обязательной видеокарты. На Windows используется Docker Desktop с WSL2 и подходящим драйвером NVIDIA; на Linux нужен настроенный NVIDIA Container Toolkit. Выбранный режим и фактическую загрузку весов на GPU можно проверить через `ollama ps` внутри контейнера.

Для поддержанных репозиториев Unsloth используется прямой импорт GGUF через `scripts/prepare-model.mjs`: загрузка через HF/Ollama registry во время проверки многократно останавливалась на сгенерированных метаданных. Инициализатор получает ревизию Hugging Face и использует её для списка файлов и скачивания, выбирает точное имя квантизации и LFS SHA-256, проверяет размер. Уже существующий blob обнаруживается через HEAD; новый файл передаётся потоком в Ollama, которая проверяет его SHA-256. Затем `/api/create` импортирует GGUF с настройками семейства. При временных сетевых ошибках допускаются три попытки с паузами 2 и 4 секунды; постоянные ошибки метаданных, HTTP 404 или несовпадение digest останавливают подготовку. Другие модели используют загрузку через Ollama registry с тем же пределом повторов.

## Следствия

Локальное применение фильтра позволяет сохранять поиск при live-изменении метрик: обновляются результаты, а модель не вызывается на каждый SSE-пакет. Обычный поиск по названию использует debounce 250 мс. Умный разбор запускается по кнопке или Enter, чтобы ввод каждого символа не создавал сетевой запрос. Изменение строки отменяет незавершённый разбор и снимает прежний структурированный фильтр; проверка текущей строки и `AbortSignal` не позволяет применить запоздавший ответ.

Схема ограничивает технически допустимый результат, но не доказывает, что модель верно поняла естественный язык. Поэтому интерфейс показывает способ разбора и применённые условия, включая OR-группы, сортировку и лимит. Качество проверяется отдельно на примерах с ожидаемыми фильтрами; прохождение проверки схемы не считается проверкой смысла. Локальная модель остаётся экспериментальной: возможны потерянные условия, неверные операторы, числа или переход в текстовый поиск для допустимой фразы. [Подробные результаты](../search-model-evaluation.md) разделяют старую и расширенную схемы, настройку инструкции и итоговое сравнение моделей. При отказе модели или недопустимом ответе выполняется явно обозначенный поиск по названию.

Веса сохраняются в отдельном Docker volume. Повторный запуск проверяет renderer, parser и, для Gemma, обязательный stop-токен через `/api/show`, затем использует локальную копию без обращения к Hugging Face. Кэш с другими настройками переимпортируется. После загрузки выполняется ограниченный прогрев: синтетический текст и один выходной токен, без данных компании. Готовность требует завершённой генерации с положительным `eval_count`; простая загрузка файла в память недостаточна, поскольку первый GPU-prefill может быть долгим. До готовности в кнопке умного поиска показан спиннер с подсказкой об этапе; кнопка и Enter не отправляют запрос модели. Обычный поиск и остальные функции доступны. Клиент периодически проверяет состояние и автоматически включает кнопку после подготовки; при ошибке показывает объяснение и продолжает проверять восстановление. Полные загрузки Qwen и Gemma GGUF с последующим native-импортом, прогрев Qwen Q8 на GPU и повторные запуски из кэша проверены в Docker. Для смены модели меняется `OLLAMA_MODEL`; формат фильтра остаётся общим. Реальная работа внешнего OpenAI зависит от заданного ключа и доступности API; наличие интеграционных тестов с подставленным ответом не означает выполненный платный запрос.
