# Модель данных

## Исходный узел

API возвращает массив `OrgNode`; пустой массив является корректным ответом.

```ts
interface OrgNode {
  id: string;
  name: string;
  parentId: string | null;
  headcount: number;
  budget: number;
  performance: number;
  updatedAt: string;
  employees?: OrgEmployee[];
}

interface OrgEmployee {
  id: string;
  name: string;
  role: string;
}
```

| Поле          | Значение и ограничения                                                            |
| ------------- | --------------------------------------------------------------------------------- |
| `id`          | Непустая строка, уникальная во всём наборе                                        |
| `name`        | Непустое название подразделения                                                   |
| `parentId`    | ID существующего родителя либо `null` для корня                                   |
| `headcount`   | Собственная численность: неотрицательное безопасное целое число                   |
| `budget`      | Собственный месячный бюджет в рублях: конечное неотрицательное число              |
| `performance` | Собственная эффективность в процентах: конечное число от 0 до 100                 |
| `updatedAt`   | Корректная ISO-дата со временем и часовым поясом, например `2026-09-14T12:00:00Z` |

Числа в строках не преобразуются автоматически. Проверка даты отвергает невозможные календарные даты, например 30 февраля. Импорт копирует только поля схемы. Дубликаты, отсутствующие родители, циклы и ссылки узла на себя отвергаются до публикации данных. У каждого узла один родитель; несколько корней разрешены. Проверка и обходы выполняются итеративно.

Уровень вычисляется из связей: корень — дивизион, глубина 2 — отдел, глубина 3 — команда. Уровень не хранится в API. Более глубокие уровни допустимы для графа и общих расчётов, но фильтр по именованным уровням ограничен 1–3. Порядок корней и соседей соответствует порядку исходного массива; родитель может находиться после ребёнка.

## Состав сотрудников

`employees` расширяет исходный контракт задания. Если список передан, его длина обязана совпадать с собственной численностью `headcount`; каждая запись содержит непустые `id`, `name` и `role`. ID сотрудника уникален во всём наборе, поэтому один человек не может одновременно принадлежать двум подразделениям. Список и его записи копируются при валидации. Отсутствие поля означает, что API передал только показатели; клиент не придумывает сотрудников.

Демонстрационный сервер передаёт состав для всех подразделений, включая дивизионы и отделы. Имена и должности вымышлены, ID стабильны: при изменении численности сохраняются записи оставшихся сотрудников. Список ограничен 1000 демонстрационными сотрудниками на узел. Это отдельные записи внутри подразделения, а не дополнительные узлы оргструктуры, поэтому число подразделений и агрегаты не увеличиваются повторно.

В дереве счётчик показывает общую численность поддерева. Раскрытая ветвь содержит вложенные подразделения и список собственных сотрудников. Команды раскрываются до людей; пустая команда показывает пустое состояние. Список меняется вместе с численностью, не сбрасывая состояние раскрытия.

## Собственные и суммарные показатели

Показатели записи относятся только к этому узлу. Например, сотрудники отдела могут обозначать руководителей отдела, а сотрудники команд — состав каждой команды. Если записать в родителя уже суммарное значение, клиент повторно учтёт потомков.

Для узла `v` множество `S(v)` включает сам узел и всех потомков:

```text
headcount(v) = Σ headcount(u), u ∈ S(v)
budget(v) = Σ budget(u), u ∈ S(v)
performance(v) = Σ (performance(u) × headcount(u)) / headcount(v)
nodeCount(v) = |S(v)|
```

Если общая численность равна нулю, агрегированная эффективность равна `null`: она не определена. Такие строки не удовлетворяют числовому условию по эффективности. Нулевая численность не отменяет собственный бюджет подразделения.

Пример: у отдела 2 сотрудника с эффективностью 50%, у вложенной команды — 8 с эффективностью 90%. Для отдела таблица покажет 10 сотрудников и `(2 × 50 + 8 × 90) / 10 = 82%`. Простое среднее двух процентов дало бы неверные 70%. Округление применяется при выводе, не при агрегации.

## Индекс и снимок клиента

`OrgIndex` содержит `nodesById`, `childrenById`, `rootIds`, `depthById` и `postOrderIds`. Карты обеспечивают доступ по ID, а порядок «дети перед родителями» позволяет вычислять агрегаты без рекурсии. `OrgAggregate` содержит `headcount`, `budget`, `performance` и `nodeCount`.

Кэш клиента хранит индекс, карту агрегатов, серверный курсор и карту изменившихся полей. Структура отделена от метрик: пакет числовых изменений сохраняет карты детей, глубин и порядок обхода. Временная метка описывает изменение данных, а порядок доставки определяется курсором.

## Пакет изменения метрик и сотрудников

```json
{
  "previousCursor": "example-instance:41",
  "cursor": "example-instance:42",
  "changes": [
    {
      "id": "frontend",
      "budget": 3850000,
      "performance": 94,
      "updatedAt": "2026-09-14T12:01:00.000Z"
    }
  ]
}
```

В каждой записи обязательны `id` и `updatedAt`; `headcount`, `budget`, `performance` и замена массива `employees` могут присутствовать независимо при согласованном результате. Для узла со списком изменение численности требует соответствующего списка в том же пакете, в том числе `employees: []` при нулевой численности. Неуказанные данные сохраняются. Изменения проверяются атомарно, включая уникальность сотрудников между подразделениями. Структурные и посторонние поля запрещены. Неизвестный ID, повтор одного ID внутри пакета или некорректное значение отвергают весь пакет. Переименование и перенос подразделений требуют нового полного снимка.

`changedFields` отмечает собственные изменённые метрики и изменившиеся агрегированные поля предков. Изменение только имён, должностей или состава при прежней численности обновляет исходную запись, сохраняя карту агрегатов. Полностью идентичный пакет сохраняет исходные объекты индекса и агрегатов; одинаковый HTTP-снимок сравнивается по содержимому списков, а не по ссылкам на новые массивы.
